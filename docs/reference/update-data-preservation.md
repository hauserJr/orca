# Update data preservation
**Authority and scope:** Application files are replaceable; the existing user-data directory is not. Profile settings, projects and workspace state remain in `profiles/<id>/profile-state.db`; workflows and human questions remain in `orchestration.db`. Agent credentials, session journals, documents and terminal history retain their existing owners and paths. Nothing here initializes a second writable database or resets defaults.
**Automatic update path:** `src/main/startup/main-window-core-services.ts` and `main-process-runtime-launch.ts` call `preserveStateBeforeUpdateRestart` with mandatory failure handling. `src/main/update-restart-preservation.ts` now requires credential synchronization, a full profile checkpoint, and a completed `createUpdateProfileSnapshot` before returning. `src/main/updater/updater-install-execution.ts` invokes the native installer only after that gate. Failure or the existing 90-second deadline aborts installation. `src/main/updater/updater-setup.ts` disables implicit install-on-quit so it cannot bypass the gate.
**Backup format:** `src/main/update-profile-snapshot.ts` stores a unique snapshot beside the user-data directory, under `<directory-name>.update-backups/<timestamp>-<uuid>/`. The `data` tree preserves files; `manifest.json` records the application version, completion time, relative paths, links and SHA-256 hashes. `update-snapshot-file.ts` protects new backup/restore directories with the existing Windows DACL implementation or private Unix modes before writing contents. SQLite snapshots use the existing asynchronous online backup implementation, include committed WAL data, validate integrity and publish standalone files. `update-sqlite-snapshot.ts` handles exclusively locked Chromium databases by comparing all captured DB/WAL/journal hashes before and after capture, recovering only the private copy, then validating the resulting database. LevelDB captures verify their entire file set before/after and omit only the empty process lease `LOCK`. Windows native SQLite paths use extended-length names. A failed snapshot has no completion manifest. Browser caches, diagnostic logs and process rendezvous sockets are excluded; symlinks are recorded without traversing external directories. External project repositories and external agent homes are never overwritten or migrated by this change.
**Restore behavior:** `src/main/update-profile-restore.ts` validates paths and every checksum before creating a new destination. Existing destinations, traversal, link ancestors and damaged copies are rejected. Restored files are checked again and flushed. The current profile is never overwritten by this operation. Keep the previous application installer separately: a data snapshot is not an application-binary rollback.
**Manual installer preparation:** A standalone installer or OS package manager does not run the in-app update callback. Before using that path, stop writes to the selected profile and explicitly run the backup command below. Do not treat launching an installer directly as covered by the automatic backup gate. Do not run NSIS uninstall/install experiments against the user's active application or daemon.
**Commands:** Run from the repository using Node 24 with `node:sqlite` backup support and the installed dependencies. Substitute the already-established profile path; never point these commands at an application installation directory.

```text
node node_modules/tsx/dist/cli.mjs config/scripts/update-profile-snapshot.ts backup <existing-profile> <backup-root-outside-profile>
node node_modules/tsx/dist/cli.mjs config/scripts/update-profile-snapshot.ts restore <completed-backup> <new-empty-path>
```
**Recovery sequence:** Stop the application and profile-owning processes normally; retain the current profile as a separate failed-upgrade copy. Restore into a new path and verify completion, install the matching previous application version, then move the verified restored directory to the original profile location while all owners are stopped. Preserve the failed-upgrade copy until recovery is confirmed. Do not merge database/WAL files from different snapshots, delete credentials, or reset settings to make startup succeed. OS-bound encrypted credentials require the original OS account; cross-account migration is not supported by this procedure.
**Test2 packaging:** `config/test2-profile.cjs` binds the established external profile to `<appData>/Orca Test2/profile-location.json` on its first successful launch. Later packaged pointers cannot redirect it. `config/test2-bootstrap.cjs` requires an existing profile/index outside the installation directory and no longer creates a missing directory. `config/electron-builder-test2.config.cjs` packages the resolver and selects `config/nsis/orca-test2-profile.nsh`. Its installer initialization saves the established installation's pointer before uninstalling the old version; the shared install hook restores it after application-file replacement. An established install missing its pointer, or a failed pointer copy, aborts with exit code 2. This also covers the first transition from builds without a persistent binding. Test2 has no official update feed.
**Compatibility and restart:** The Work Inbox table/status vocabulary is unchanged. `workInbox.reopen` is additive and old hosts may reject it as unsupported; the client never treats this as successful reopening. Daemon-backed PTYs retain their existing disconnect/reconnect path; `killAllPty` only kills in-process local PTYs. Persisted inbox IDs survive reopening of their database; clients resume the original ID after transport interruption. A filesystem snapshot is not an atomic transaction spanning every independently active database or remote host.
