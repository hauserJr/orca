# Opt-in agent question routing

**Scope:** This follow-up depends on the Work Inbox CLI/MCP interface. Add `ORCA_WORK_INBOX_ROUTING=1` to a local Codex or Claude agent's launch environment to attach the built-in question tools and routing instructions. Existing launches without this value are unchanged. This does not turn native provider permission requests into approval, change account configuration, or restart existing conversations.
**Terminal flow:** The common `spawn-options-assembly.ts` calls `prepareAgentWorkInboxLaunch`. It keeps the existing Codex no-daemon preparation and skips SSH/WSL routing. Claude receives a profile-private MCP config; Codex receives invocation-only MCP config and effective developer instructions read from its selected configuration. Caller identity is passed at launch, never saved to an agent home.
**Native chat flow:** `claude-work-inbox-options.ts` merges existing prompt, MCP servers and allowed tools without granting shell or file permissions. Codex adds the MCP launch arguments, opens/resumes its thread, and appends a routing message before accepting user work. An opted-in provider that cannot preserve its instructions or rejects the required method fails startup; it does not silently claim routing is active.
**Question contract:** An agent supplies an immutable request ID, retains the returned question ID on timeout, waits on that ID, and acknowledges an answer before continuing. Closing a question returns cancellation with no answer and is explicitly not approval. The original account, conversation, tool restrictions and execution host remain authoritative.
**Tests:** `work-inbox-launch.test.ts` covers generated shell arguments, option boundaries, caller identity, remote exclusion, opt-in behavior and instruction preservation. `codex-work-inbox-session.test.ts` covers fresh/resumed native sessions and rejection. The Claude stream connection suite inspects actual SDK child argv. `tests/e2e/work-inbox-mcp-launch.spec.ts` launches the generated MCP command against a disposable Electron profile, asks through stdio, closes the visible question via CDP, and receives cancellation through the same MCP client. Existing Codex isolation and MCP tools suites are adjacent regressions.
**Known limits:** Only local Codex/Claude launches are configured here. This does not attach tools to an already running terminal, inject prompts into every other provider, or configure an older remote peer. Real model turns are not needed by the isolated contracts and are not claimed as tested. A local Codex app-server was additionally checked with an empty home for config/read, thread/start and thread/inject_items without starting a model turn. Native Linux/macOS, SSH and real Claude login remain separate validation.
**Coverage correction:** The existing Codex identity assertion assumed a POSIX CLI filename and rejected Windows drive paths and `.cmd` shims. That failure was reproduced on the unchanged inbox base before correcting the platform-specific assertion. Launch/routing changes must run the named source, SDK and MCP integration cases.
