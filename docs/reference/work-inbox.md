# Work Inbox v1
**Purpose:** Agents explicitly ask the human in Orca. The human reads and answers in the sidebar Work Inbox, grouped by project and individual agent. Internal coordinator mail remains separate.
**Scope:** Human questions, answers, closing without answering, history, reopening, waiting and acknowledgement. Answered and closed cards leave the unanswered list; history retains them. General notices, document management, automatic extraction from terminal prose, and provider permission/login dialogs are outside this version.
**Authority:** `src/main/runtime/work-inbox/work-inbox-store.ts` owns the additive `work_inbox_items` table inside the existing orchestration SQLite database. The renderer and MCP server are clients of that state, not additional writable stores.
**Identity and routing:** `src/main/runtime/work-inbox/work-inbox-service.ts` resolves project and agent metadata from the runtime. Every resume and acknowledgement must belong to the original asking agent. Human answers and cancellation require an authenticated desktop or paired-device UI caller. Local CLI clients cannot act as the human.
**Contract:** `src/shared/work-inbox.ts` defines validation, status, options, revision checks, and request identity. `WorkInboxListParams.id` is an optional exact-question read (1–256 characters); omitting it preserves existing list behavior. The store ANDs this ID with the original view, project and agent filters using a bound SQL parameter; the workspace permission and all write/ACK checks remain unchanged. `src/main/runtime/rpc/methods/work-inbox.ts` registers the runtime methods through `src/main/runtime/rpc/methods/index.ts`.
**States:** `open` means awaiting a human; `answered` means the answer is durable; `delivered` means the asking client explicitly acknowledged receipt; `cancelled` means the user closed the question without an answer and never implies permission to continue. The card X invokes the existing human-only cancel method without sending the selected draft. `workInbox.reopen` uses the same ID and a revision check; the last closure timestamp remains recorded. Waiting asks observe a closure even if immediately reopened. Returning from a server handler alone does not prove receipt.
**Agent entry:** `orca inbox ask --question "Which approach should I use?" --options "A,B" --request-id <uuid> --json`. A timeout preserves the question; resume its exact ID with `orca inbox ask --resume <id> --json`. Preserve the original request ID and immutable intent after an uncertain create result.
**MCP entry:** `orca inbox mcp` uses standard input/output, the official MCP SDK, and the agent identity injected by Orca. It exposes `ask_user`, `wait_for_answer`, and `acknowledge_answer`; it exposes no human-answer tool. `src/cli/work-inbox-mcp-tools.ts` owns the tools; `src/cli/handlers/work-inbox-mcp.ts` uses the authenticated runtime client.
**Built-in provisioning:** Managed launches use one service: `orca inbox ask` or the `orca inbox mcp` stdio bridge when an agent has no shell. Orca supplies invocation-only tool wiring and exactly three built-in permissions. No project MD, agent settings, role permissions or credentials are rewritten. `src/main/runtime/work-inbox/work-inbox-cli-launch.ts` owns server configuration, caller stamps and tool names; `work-inbox-agent-launch.ts` connects both PTY spawn lanes. The model registry supplies launch syntax, rather than separate question implementations.
**Managed guidance:** `src/shared/managed-agent-startup.ts` adds the input route while the low-level planner retains quoting and transport rules. Launch-line and post-ready paste lanes carry the original task once. Empty launches load the route and wait for work. Native tool-capable providers also receive the route at startup/resume; saved conversation ID, role, model, effort, existing MCP servers and file restrictions are preserved. `src/main/claude/claude-work-inbox-options.ts` merges the same CLI bridge into structured sessions.
**CLI wait/receipt:** Without explicit `--timeout-ms`, `src/cli/handlers/work-inbox-ask.ts` resumes the same question across host long-poll deadlines until answer or cancellation. It prints the answer, flushes stdout, then requires receipt success before exiting 0. A refused/lost receipt is a failed command even when an answer was printed. Explicit timeouts and transport failures retain the original ID. MCP tools use bounded waits and explicit ACK on that same service.
**Agent instructions:** Ask only questions that require a human decision. Use a fresh UUID for a new immutable question. After an uncertain send, retry the same request ID and arguments. After a pending result, call `wait_for_answer` on the original ID. Read the answer, call `acknowledge_answer`, and continue the task. A timeout or cancellation is not approval.
**UI:** `WorkInboxSidebarEntry.tsx` polls a bounded open count while closed and shows `!` for confirmed unanswered questions. `WorkInboxSheet.tsx` offers unanswered/history views and project/agent filters. Each open card has an X to close without sending its draft; closed cards in history can reopen. `use-work-inbox.ts` tracks explicit answer receipt, while `use-work-inbox-status.ts` handles revision-checked close/reopen on the selected execution host. `WorkInboxAgentConnection.tsx` sends fixed routing guidance to a positively idle, host-verified original supported agent process; a persisted UUID reuses the terminal prompt receipt ledger after lost replies or reload. Unverifiable or remote guidance targets refuse safely.
**Ordinary Codex routing:** `src/main/codex/codex-work-inbox-launch.ts` attaches one invocation-scoped MCP server after any resume subcommand and preserves user configuration, effective developer instructions, other servers and non-Inbox permissions. An enabled-tool allowlist and per-tool invocation approvals authorize only ask/wait/ack. Caller identity comes from the current launch environment, never shared-home registration. `codex-structured-session-acquire.ts` appends policy through `thread/inject_items` while preserving saved thread instructions. Agent-side CLI compatibility uses `inbox ask --no-ack` plus explicit `inbox ack`; humans answer entirely in Inbox. SSH/WSL managed launches and cmd-shell instruction delivery currently refuse safely.
**Persistence and compatibility:** The table definition is in `src/main/runtime/work-inbox/work-inbox-row.ts`; it is additive and created idempotently by `src/main/runtime/orchestration/db/schema/create-tables.ts`. Older peers lack these RPC methods and must report an unsupported feature; never silently send to another runtime. No user-data migration or reset is needed. Deploy the runtime before using the new UI/CLI/MCP tools; keep the database on rollback so pending answers survive.
